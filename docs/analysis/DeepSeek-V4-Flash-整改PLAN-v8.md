## J00 取消和deadline必须停止原轮，并正确报告

文件：content的原轮校验、storage监听、异步工作记录、background终态/超时协议及相关driver。

实施：

1. 给每轮明确的active/cancelled/expired状态；原轮验证同时检查该状态，而不只检查runId、URL和档案修订。
2. 档案修订/用户取消/新轮替换发生时：停止排队回调和后续副作用，清理该轮pending登记，并向后台报告cancelled。不要等后台25秒后误报“页面无响应”。
3. 后台deadline发生时，向本轮参与frame发送有作用域的停止通知；content核对run/document后失效原轮。已写值保留，不借取消自动撤销用户数据。
4. 超时或取消后，旧Promise即使返回也不得写、点击、覆盖新轮UI或重新发成功终态。晚消息得到明确拒绝，不污染新轮。
5. 成功、等待人工、取消、超时各有准确提示；PANEL_FILL收到superseded/cancelled时不显示“未登录/无法开始填写”，也不解锁另一个正在执行的新轮。
6. 待验证结果清理与后台统计规则一致：已完成字段可保留，未完成字段明确标未完成；不能丢掉所有结果让total变0来假装收口。
7. 保留本轮规则：轮询40次仍pending时绝不强行done；终态后的定时补填不得执行。不得恢复旧的“15秒+常数就是完成”。

强制验收：

- 改档案时取消正在等待的日期/依赖/picker或行任务；取消后无新写，及时收到cancelled而不是25秒timeout。
- 本地测试构建缩短deadline，构造比deadline更慢的任务；超时后无write/click，Promise迟到不改变终态。
- 两轮交错：旧取消响应不覆盖新轮状态，不提前启用新轮互斥按钮。
- 12秒选项新场景仍通过（10.5秒仅顶层1项，15秒补填后全页5项且失败1项）。
- 移除“deadline使原轮失效”后对应负例必须失败。使用临时测试构建或既有VM入口，不给正式扩展增加任意测试执行消息。

## J01 人工接管后的续轮必须与“终态即最终”一致

问题：后台冻结waiting-manual结果，但人工完成后content可能仍在原轮继续执行。必须选择并实现一个一致方案，不能只更新本地高亮。

文件：picker-handoff、completeManualPicker/resumePickerQueue、终态协议、aggregation与UI。

实施：

1. 明确状态：推荐将等待人工作为可恢复暂停，或者在用户确认后创建与上一轮关联的新run；只能采用一种一致的数据流。
2. 若暂停：暂停不是不可更新的最终结果，自动任务结束后显示等待人工；后台等待策略有明确生命周期和容量边界，不把正常人工等待报成页面失联。
3. 若采用新run：用户完成/确认触发新的原轮快照与参与者登记，旧轮不再写。继续之前重新读取档案与验证绑定，不能沿用失效profile或代码名称。
4. 人工已选同值不要重复点击/发事件；“本轮内不再重试”仍有效，新显式填写可重试。不要重新引入安全辅助或整页兼容门槛。
5. 重新验证父picker后再释放依赖者，保持独立字段和动态行继续可用；后台汇总与本地结果都反映续轮。
6. 导航、档案变更或用户取消期间的人工回调失效，不得凭“卡片还在”恢复权限。

强制验收：

- 真实扩展本地夹具：自动picker转人工→用户在页面完成→扩展确认→依赖子项填写→最终汇总更新。
- 再读后台消息/本地counts核对结果，不能只看绿色标记。
- 等待期间取消/换档案/替换控件后不继续；跳过当前轮后不自动重开；新点击能再试。
- 若后台拒绝续轮结果，测试必须失败，不允许把失败隐藏成“证明层级保留”。
